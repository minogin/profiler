# Первый прогон — план

Составлен 19.08.2026. Решение по итогам обсуждения: **начинаем с чистого листа, ни с чем не интегрируемся.** Мосты (async-profiler, JFR) — потом, к уже работающей вещи.

Цель первого прогона — не инструмент, а **одно число: расхождение измеренной доли операции с заданной.** Всё остальное существует ради того, чтобы это число получить.

Стек: Kotlin/JVM, Gradle. Вывод — в консоль. Ни файлов, ни UI, ни корутин.

---

## Фаза 1 — стенд

Синтетическая нагрузка, где истинный ответ известен заранее.

20 операций с заданными длительностями, N рабочих потоков, прогон минуту. Операции крутятся в цикле по заданному распределению вызовов. На выходе — таблица «операция → истинная доля времени».

<sub>**Для Claude Code.** Истина берётся двумя независимыми способами, и они должны сойтись между собой: (а) конфигурация — заданная длительность × заданное число вызовов; (б) замер — операции гоняются батчами, `nanoTime` стоит вокруг батча, не вокруг вызова, накладные расходы размазываются. Длительность операции задаётся busy-loop'ом с калиброванной ценой итерации, не `Thread.sleep`. Обязательно заложить сразу: перекос длительностей на два порядка (20 нс против 2 мкс — метод должен ловить обе), вложенные операции (одна вызывает другую), и режим искусственного голодания, где работой заняты заведомо 3 потока из 16 при остальных простаивающих. Последнее нужно фазе 4, дописывать потом будет дороже.</sub>

## Фаза 2 — сэмплер

Слот на поток, отдельный поток-сэмплер, счётчики.

Вход в операцию — запись номера в слот, выход — восстановление прежнего значения (не обнуление, иначе ломается вложенность). Сэмплер раз в ~1 мс обходит все слоты и инкрементит счётчики по номерам.

<sub>**Для Claude Code.** `@Volatile @JvmField var current: Int` в объекте-слоте, слоты живут в массиве или в разреженной карте «поток → слот», регистрация потока при первом входе. Функция входа — `inline`, чтобы не платить за мегаморфный вызов. Шаг сэмплера сделать параметром, не константой: он понадобится фазе 3. Сэмплер читает чужие слоты без синхронизации — это осознанно, проверяется в фазе 3. Счётчики — обычные `long`, у сэмплера единственный писатель.</sub>

## Фаза 3 — сверка

Ради этого всё и пишется. Сэмплер гоняется поверх стенда, измеренные доли кладутся рядом с истинными.

Три гипотезы закрываются одним прогоном:

1. **Метод работает на наносекундных операциях** — доли сходятся, несмотря на то что отдельный вызов короче шага сэмплера на четыре порядка.
2. **Наблюдатель не влияет на наблюдаемое** — тотал стенда с метками и без отличается мало.
3. **Чтение слота без синхронизации не смазывает картину** — если сходится, вопрос закрыт эмпирически, рассуждать про модель памяти не нужно.

<sub>**Для Claude Code.** Вывод: таблица «операция / истинная доля / измеренная доля / расхождение», отсортированная по расхождению. Прогон повторяется на нескольких шагах сэмплера (1 мс, 5 мс, 20 мс) и нескольких длительностях (10 с, 60 с, 300 с) — расхождение должно падать с ростом числа сэмплов, и это падение само по себе подтверждение метода. Отдельный прогон — стенд без единой метки, только тотал, для гипотезы 2. Ожидаемая точность: операция с долей 5% при полумиллионе сэмплов набирает тысячи попаданий, так что расхождение в единицы процентов — норма, в десятки — что-то сломано.</sub>

## Фаза 4 — состояние потока и коэффициент параллелизации

Только после того, как фаза 3 сошлась.

В сэмпл кладётся не только метка, но и состояние потока. Отсюда гистограмма занятости — какую долю времени работал 1 поток, 2, 3, … N — и эмпирический коэффициент параллелизации как среднее по ней.

Различить «выполняет операцию» и «крутится в диспетчере» изнутри нельзя — и то, и другое RUNNABLE, а диспетчер не инструментирован. Рабочая эвристика: пустой слот при RUNNABLE — почти наверняка диспетчер, пустой слот при WAITING — простой. Проверяется на режиме голодания из фазы 1.

<sub>**Для Claude Code.** Состояние берётся из `Thread.getState()` в момент обхода. Гистограмма считается по срезам: один тик сэмплера — один срез, в нём число потоков с непустым слотом. Ключевой вывод — два графика при N = 1, 2, 4, 8, 16: число занятых потоков и пропускная способность. Расходятся (занятость растёт, пропускная нет) — упёрлись в память; занятость упирается в потолок — проблема со снабжением работой. Длина очереди диспетчера в сэмпл пока не пишется, это следующий заход.</sub>

## Фаза 5 — корутины

Вне первого прогона. `ThreadContextElement`, `updateThreadContext` / `restoreThreadContext`, замер цены крючка на реальной частоте диспетчеризации. Подробности — в дизайн-документе по сэмплированию.

## Правки в дизайн-документ по сэмплированию

Две вещи, которые обсуждение изменило:

- В разделе «Что проверить перед реализацией» **снять первый пункт** — про то, достаётся ли `Profiler.currentLabel()` и есть ли блочный вызов. Пишем своё, get/set тривиально есть, в чужие исходники смотреть не надо.
- В «Известное окружение» **дописать**: мост к async-profiler непригоден для коэффициента параллелизации в принципе. Он сэмплирует каждый поток по своему сигналу таймера, одновременного среза всех потоков там нет — величина восстанавливается только бакетированием по времени, с перекосом. Свой сэмплер даёт срез прямо, потому что он один и обходит все слоты за проход.
